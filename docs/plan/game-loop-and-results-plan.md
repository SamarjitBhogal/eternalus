# Game loop and results plan

**Purpose.** Read this before you build the match director, scoring, the victory condition, the
win/lose screen or the post-game screen. It orders the owner's request of 2026-10-27 against
architecture [12](../architecture/12-game-story-and-match-director.md) and
[13](../architecture/13-game-interface.md). It decides only architectural choices (§5a). Every
product or game-design point goes to the owner as a GL-Q question (§5b).

**Status.** Proposed; the owner answered every GL-Q on 2026-10-28 (§5c, which wins over older
text here). The frontmatter says `draft` because `npm run docs:check` accepts only `draft`,
`active` and `deprecated`. Nothing in it edits a design doc: §6 lists the design-text changes for
the owner.

## 4. Target design

The design follows architecture 12 and 13. Deviations are marked **Deviation** and §5a says why
each is acceptable or better than the docs. §5a also names the rejected lazier option for each
choice (ponytail lite); the architecture wins where they differ.

### 4.1 Core: `packages/core/src/match/` (12 §1 to §4)

- `MatchDirector` (12 §4): per tick, in this fixed order: fire due timeline entries, run the
  current phase's `update`, fold scoring, check victory conditions, end.
- `MatchDirectorSystem` (`systems/`): a thin adapter. It runs after `DeathSystem` and before
  `InvariantSystem` in `DefaultSystemPipeline`. It does nothing once `state.match.result` is set.
  `Simulation`'s constructor builds the director and injects its content values (§4.4).
- Phases: one `MatchPhaseState` class per phase under `match/phases/`, registered only in
  `defaultMatchPhases.ts`. Transitions are forward only. `GameState.setPhase` emits
  `phase-changed` and stamps `phaseEnteredTick`.
- Timeline: `GameConfig.match.timeline` (`MatchTimelineEntry[]`, 12 §3), resolved to ticks once by
  `MatchTimeline.resolve`. `validateGameConfig` gains the 12 §3 rules. This plan builds two action
  handlers: `enter-phase` (GL-1) and `spawn-sovereigns` (GL-3, §4.3). `announce` waits for a consumer:
  until then `MatchBridge` announces from `phase-changed`, as 12 §8 designs. `summon-greater-boss`
  and `spawn-mini-bosses` are registered by sprint 3.6 when the bosses exist (GL-Q19).
- The owner's loop items map onto the timeline as follows. No item needs director logic beyond
  timeline entries.

| Owner item            | Mechanism                                                                                                                                                       | Owner of the effect                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| initial countdown     | `countdown` phase from tick 0; entry `countdown-over` at `countdownSeconds` enters `early-game`                                                                 | this plan                                    |
| host deployments      | `SpawnSystem` spawns opening hordes at tick 0; tower waves wait for the countdown (design: `SpawnWave.afterTick`; M1: computed from `countdownSeconds`; §5a A7) | M1 (Samarjit)                                |
| camps on              | `Spawner` activation data consumed by `SpawnSystem` (12 §2 `early-game` row); the tick is GL-Q16                                                                | M6 (Samarjit; needs `Camp`, sprint 2.1)      |
| crystal eruption      | entry `mid-game` at a fraction of `plannedMatchSeconds`; action `summon-greater-boss`                                                                           | this plan (entry); sprint 3.6 (boss, GL-Q19) |
| tower and wall status | structure entities' `Health` in the snapshot; breakability through `structure-breakability-changed`                                                             | sprints 2.1 and 2.4 (GL-Q19)                 |
| win condition         | `ObjectiveLostCondition` in `defaultVictoryConditions.ts`; the sovereign carries `WinObjective` (§4.3)                                                          | this plan                                    |

**Type homes (§5a A2).** `MatchPhase` moves from `state/GameState.types.ts` to
`config/matchPhases.ts`, beside `MatchTimelineEntry`. It is derived from the `as const` array
`MATCH_PHASES` in that file, which is the single phase order. `VictoryConditionId` sits in
`config/VictoryConditionId.types.ts`, so `content/` can key the verdict lines by it (02 §2:
`content/` may import `config/` types, not `state/`). `MatchState`, `MatchResult`,
`LegendStats`, `TeamStats`, `ScoringState` and `Verdict` live in `state/`, as 12 §4's
`state/MatchState.types.ts` sketch already does for `MatchState`. Behaviour stays in `match/`.
`index.ts` re-exports the same names. Ids that `config/` holds but cannot type
(`AnnouncementId`, later sprint 3.6's `SpawnTableId` and `BossId`) stay plain strings in
`config/`, checked against content where content is visible. `PhaseMonotonicInvariant` gets the
phase order injected at construction, because `diagnostics/` may import only the types of
`config/` (02 §2, DEC-20). `Simulation` passes `MATCH_PHASES` into
`diagnostics/DefaultInvariantRunner.ts`, as it passes `curves` today.

### 4.2 Snapshot and events for the HUD

```ts
// Sketch: packages/core/src/state/Snapshot.types.ts (addition)
export type MatchSnapshot = {
  readonly phase: MatchPhase;
  readonly phaseEnteredTick: number;
  /** The unfired timeline entries in tick order; empty after the last one. */
  readonly upcoming: readonly { readonly entryId: string; readonly tick: number }[];
};
// Snapshot gains: readonly match: MatchSnapshot. Snapshot.phase goes in GL-1 (callers move to match.phase).
```

- `upcoming` is `state.match.schedule` from `timelineCursor` on. `schedule` is the resolved
  `{ entryId, tick }[]`, stored as plain data in `state.match` when the match is built:
  `GameState.snapshot()` builds the snapshot (03 §12), and `state/` may not import `match/` (02 §2).
- A client selector picks the mark to count down to from `upcoming` (the countdown end, then the
  eruption), by entry id. Which marks the HUD shows is GL-Q16 (d). The mark labels are core content
  (`content/narrative/`, keyed by timeline entry id), exported through `loadDisplayContent()` and
  read through `contentSlice` (13 §3, rule 11).
- `MatchBridge` adds `match` to the `match-clock` publish (every 6 ticks). No new bridge event is
  needed for the timers.
- Tower and wall status: once structures are entities, `MatchBridge.structuresOf` reads each
  feature's entity `Health` (the snapshot already carries `health`). Breakability needs one more
  snapshot field on structures; it comes with sprint 2.4, not this plan.
- Core events added to `GameEventMap`: `match-ended { result: MatchResult }`. `phase-changed`
  starts to be emitted.

### 4.3 Victory: the sovereign (12 §6, ADR 0021)

```ts
// Sketch: packages/core/src/config/VictoryConditionId.types.ts. 12 §6 declares the other ids;
// `stronghold-destroyed` and `score-cap` are dropped (§5c GL-Q2, GL-Q16 (a)).
export type VictoryConditionId = 'objective-lost' | 'forfeit' | 'aborted';
```

- `match/conditions/ObjectiveLostCondition.ts` (GL-2): a buffered listener for `entity-died`. When
  the victim carries a `WinObjective` component and its team has no other live objective, the
  other team wins. If both teams lose their last objective on one tick, the result is a draw
  (§5c GL-Q7). The condition names no kind, so GL-2 tests it with a test entity that carries
  `WinObjective`, and it does not need the sovereign.
- `defaultVictoryConditions.ts` lists the conditions in check order, and the first verdict wins.
  The MVP list holds only `ObjectiveLostCondition`. A Duel mode passes its own list later (ADR
  0016, plan W10). `StrongholdDestroyedCondition` and `ScoreCapCondition` are not built.
- **The sovereign entity** (GL-3, §5a A4, §5c). A team unit that fights. An abstract `Sovereign`
  family class at depth 2 under `Unit` (family `sovereign`), and a concrete `Monarch` leaf at depth 3. One content definition (`monarch`) has a display name per team ("Emperor" by default) and a
  `WinObjective`. It also needs one `EntityRegistry` line, a client view line and a controller. A
  sovereign under `Boss` is rejected: bosses are neutral (04 §8, `BossIsNeutralInvariant`), they
  target anyone (11), and they pay boss rewards (12 §7).
- **Rules (§5c GL-Q1, GL-Q3).** It takes no damage while any BuffTower of its team lives. With no
  BuffTower entities yet the count is zero, so it can be hurt, and there is no stand-in. Every
  attacker deals full damage. Its attacks cleave. It attacks neutrals that enter. It stays in the
  throne-room zone, middle-back in the Citadel. It has a long-range attack against attackers who
  stay out of its reach and keep hitting it. After 90 s out of combat it regenerates slowly. Stats
  and rates are `TUNE`, starting from the mini-boss anchor (`balancing.md`). It never respawns,
  because its death ends the match.
- **Spawn (§5a A17).** A tick-0 timeline entry `sovereigns-crowned` runs a `spawn-sovereigns`
  action. The action emits one `spawn-requested` per Citadel with that team's sovereign, and
  `SpawnSystem` fulfils it (12 §2, §3). M1's `SpawnSystem` spawns only hordes and has no
  `spawn-requested` path, so GL-3 adds a single-unit fulfilment path to Samarjit's `SpawnSystem`.
  The sprint 3.6 boss actions reuse it, and M2 moves the spawn records onto real structures. The
  request shape is agreed with Samarjit (owner of doc 18 and `SpawnSystem`) before GL-3 starts.
  `SpawnSystem` runs before the director (18 §3.2) and fulfils requests in its own pass (03 §4), so
  the sovereigns exist from tick 1, not tick 0. The sprint 3.6 boss actions have the same one-tick
  delay. A core-only run (12 §12 `scenarios/fullMatch.test.ts`) has sovereigns and can end on
  `objective-lost`. There is no client stand-in. GL-3's unit tests spawn the sovereign with
  `dev-spawn` commands.
- `OneSovereignPerTeamInvariant` (GL-3): at most one live sovereign per team, and none spawns after
  its team has lost one. "At most one" holds on tick 0, before the sovereigns exist. A test
  triggers it.

### 4.4 Scoring (12 §5) with the owner's point model

- `match/Scoring.ts` folds a per-tick buffer of `entity-spawned`, `damage-applied` and
  `entity-died` inside the director's pass, so a match-winning kill counts. `ScoringState` sits in
  `state.match` and is hashed. `Simulation` (the composition root) passes `SCORING_WEIGHTS` into
  `new Scoring(weights)`: `match/` may import content types, not content values (12 §1).
- Rows: one `LegendStats` per Legend, registered on `entity-spawned` with family `legend` (id,
  team, class id, human or bot from `state.match.humanLegendId`, §4.5). Rows keep their data
  after the Legend dies or is removed. Events are synchronous (`GameEvents.ts`), so `Simulation`
  builds the director, and with it Scoring's subscriptions, before any construction-time spawn
  (the human seat, M3's roster). The fold runs after `DeathSystem` removed the victim, so each
  buffered record keeps the victim's family, kind and team, read in the listener.
- Columns the owner asked for: `kills` (Legend victims), `deaths`, `assists` (Legend victims
  only), `minionKills`, `score`. The other 12 §5 counters stay in the type for the Details tab and
  are filled by later work.
- Points live in content, keyed so that a new weight class is a compile error:

```ts
// Sketch: packages/core/src/content/match/scoring.ts
export const SCORING_WEIGHTS = {
  legendKill: 15, // TUNE: GL-Q10 pending ("worth the most"; no value given)
  legendKillAssist: 7, // TUNE: GL-Q10 pending
  death: 0, // owner request 2026-10-27: no negative points
  minionKill: { 'light-mob': 1, 'medium-mob': 4, 'heavy-mob': 12 }, // owner request 2026-10-27
  // structure, capture, hold: GL-Q12 (FR-007)
} as const satisfies ScoringWeights; // minionKill: Readonly<Record<MobKind, number>>
// MobKind = MobDefinition['kind'], extracted from content/mobs/mobs.types.ts by GL-4 (no such type yet)
```

- **Kill credit.** Only a Legend attacker earns a kill. A minion, turret or environment last hit
  gives no kill (GL-Q10 Recommendation). A projectile resolves to its owner.
- **Assists.** A bounded per-victim ring of `{ legendId, tick }` in `ScoringState`, fed by
  `damage-applied` from Legend attackers. On a Legend death, every other Legend in the ring within
  `assistWindowTicks` gets one assist. The window is `TUNE` in content (12 §5 says 10 s; the owner
  ruled 30 s in chat on 2026-10-19, not yet logged: GL-Q10).
- **Team score.** The sum of the team's Legend scores plus team-only points (GL-Q12).

### 4.5 `MatchResult` and the client end flow (12 §10, 13 §2)

- `end()` builds `MatchResult` (12 §10), stores it in `state.match.result`, enters `victory` or
  `defeat` for `playerTeam` and emits `match-ended`. The fields this plan fills: `winner`,
  `condition`, `playerTeam`, `hadHuman`, `durationTicks`, `seed`, `legends`, `teams`,
  `finalHash`, `configHash`. `finalHash` is `StateHasher.hash(state)` (the value `Simulation.hash()`
  returns), taken before the result is stored, so it does not hash itself. `configHash` is `fnv1a` (`utils/`) over the canonical config.
  `timeline` and `achievements` start as empty arrays and are filled by later work.
- Core inputs this needs (API change, called out in the PR, 02 §6): `MatchConfig`
  (`GameConfig.match`) gains `playerTeam` (12 §4: "chosen at match creation") and the human's
  `seat` (§5a A19). `Replay.config` then records both (15 §7), with no change to `Replay`.
  `Simulation` spawns the seat's Legend when the match is built, after the director (§4.4), and
  sets `state.match.humanLegendId` to it; with no seat it is `null` (sim mode, `hadHuman: false`).
  The spawn point follows GL-Q15; until then it is the team's Stronghold feature point, as
  `Match.spawnPlayer` uses today. `createBrowserMatch.ts` puts the setup's team and class into the
  config. `Match.spawnPlayer` and its `dev-spawn` go; `Match` takes the player's id from the
  simulation.
- The simulation keeps stepping after the end; the director is inert (12 §4).

**Client path.**

1. `MatchBridge` subscribes to `match-ended`, latches the result inside the sim event and emits
   the bus event `match-ended { result }` (new `BridgeEventMap` key, 13 §5) from `afterTick`. It
   stays the one producer of game → UI events (13 §5).
2. After `simulation.step()` returns, `Match.tick` calls `listener.matchEnded()` when the bridge
   holds a result. `RunningMatch` is created with this listener (the port gains an observer, §5a
   A8).
3. `MatchState` receives the call and schedules `transition('results')` with
   `SessionClock.schedule(0)`, so `MatchState.exit` never destroys the match inside a loop frame.
   DEC-92: the world keeps running after `match-ended`, so the move to `results` waits 5 s (the
   same `schedule` call with that delay; the value sits beside `RESULTS_COUNTDOWN_MS`, A18).
4. `connectBusToStore` writes `matchSlice.result` (type `MatchResult`, `import type` from core,
   13 §5). The result outlives `match` and is cleared by the next `match-setup`.
5. `ResultsState` gains an `enter` (it has none today). It releases the `match` asset group there
   (moved from `exit`; the match is already destroyed), loads the `selection` group the screens
   reuse (§8, `context.loadAssets`), starts `startCountdown` with `RESULTS_COUNTDOWN_MS` and
   publishes `countdown { kind: 'results' }`. On done it transitions to `menu` (MVP) or to
   `post-game` (stretch, if GL-Q8 says so). `exit` cancels the countdown. The `selection` group is
   released on each route to `menu` or `loading` and by `PostGameState.exit`. A `continue` intent
   skips the wait if GL-Q8 allows it.
6. `RESULTS_COUNTDOWN_MS` sits in `sessionTiming.constants.ts` under that file's interim note
   (§5a A18). The 30 s value traces to the owner's request.

**Win/lose for the viewer.** A bridge selector `selectMatchVerdict` compares `result.winner` with
the setup's player team: `victory`, `defeat` or `draw`. It does not read the core phase literal,
so it holds for two humans (ADR 0016).

**Results screen (MVP).** `ResultsScreen` shows the verdict, the verdict line, match duration and
the remaining seconds. The verdict line is MVP (12 §9, 13 §3): GL-5 builds the seam, core
`content/narrative/verdictLines.ts` keyed by `VictoryConditionId`, exported through
`loadDisplayContent()` and read through `selectVerdictLine`. The lines are owner wording (GL-Q6).

### 4.6 Post-game screen (stretch)

- New session phase `post-game` with `PostGameState` (R20, 13 §2). Rows: `results → post-game`
  (countdown done), `post-game → menu` (`navigate`) and `post-game → loading` (Play again, if
  GL-Q8 keeps it). The transitions table test covers each.
- The files sit flat in `ui/screens/`, as R20 and the character-select screens do.
  `ui/screens/postGameTabs.ts` is the only file that lists the tabs:

- `PostGameScreen` renders the rows that have a `Panel` through a new `ui/components/Tabs.tsx`
  (tablist, tab, tabpanel; arrow keys wrap, Home, End). `Tabs` reuses `nextRovingIndex` from
  `ui/components/rovingRadio.ts`, which already steps, wraps and handles Home and End. The screen
  never names a tab. A placeholder tab slides in by adding its `Panel` to its row; the screen does
  not change.
- `ResultsTab` reuses the `ResultsScreen` verdict block (one shared component).
- `ScoreboardTab` reads `selectScoreboard(team)`: a memoised selector that sorts `result.legends`
  by `score` high first, then by `entityId` (§5a A13). Each team is its own
  table; the player's team comes first and the player's row is marked by text and an icon, not by
  colour alone (13 §7).
- Row names: every row shows its class display name and emblem, the fields 12 §10 gives a row
  (`classId`, `controller`). The player's row (`humanLegendId`) is marked "You", and a bot row
  carries the bot icon (decisions log, Naming: "bots carry a non-spoofable icon"). Roster names
  need a key that joins a core row to a client `RosterEntry`; no task, M3 included, adds one, so
  names on rows are GL-Q6.
- The selected tab is a `useState` in `PostGameScreen`. It has no game meaning, so it stays out
  of the store.

Lazier option: reuse `SettingsScreen`'s inline tablist. Rejected, because it has no arrow-key
handling. Migrating Settings to `Tabs` is out of scope (no drive-by refactor).
